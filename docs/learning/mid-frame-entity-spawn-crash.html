Mid-Frame Entity Spawn Crash

Verified against commit cb4f6ea · created 2026-08-22 · last updated 2026-08-22
Update this record in the same change that alters what it describes (g-rule-21).

Prerequisites — you need three things. (1) How std::vector grows: that it stores its elements in one contiguous block, and that exceeding capacity() allocates a new block, copies or moves everything into it, and frees the old one — Effective STL item 14, or cppreference on vector::push_back. (2) Iterator invalidation: which operations invalidate which iterators, references and pointers — cppreference's "Iterator invalidation" table is the whole prerequisite. (3) What undefined behaviour actually means: that the standard imposes no requirement, so "it worked on my machine" is not evidence of correctness. If you have met range-for and know it desugars to an iterator loop, you are ready.

1 · What & Why

A teammate playing the Windows build reported that the game crashed in level 1-3, and — the detail that solved it — that deleting Bowser from the level file made the crash go away. On macOS the same build played 1-3 fine. That asymmetry is the whole story: the bug was not in Bowser, and it was not platform-specific code. It was undefined behaviour that one platform's allocator happened to absorb.

Every spawn in this game travels the same route. An entity that wants to create another entity cannot reach the world's entity list — it has no handle on it, deliberately — so it publishes an event, and PlayingState performs the spawn in a subscriber. Bowser breathing fire publishes EntitySpawnRequested; a question block being hit publishes PowerUpRequested. The subscriber did the obvious thing: m_entities.push_back(...).

The problem is when that subscriber runs. EventBus::publish is synchronous: it calls the handler on the publisher's own stack, immediately. Bowser publishes from inside Bowser::updateBehaviour(), which is called from Boss::update(), which is called from the for (auto& entity : m_entities) loop in PlayingState::update(). So the handler was pushing onto the very vector that loop was iterating. When that push_back exceeded the vector's capacity, it reallocated — and the loop's iterator was left pointing into freed memory, which it then dereferenced on the next iteration.

The approach chosen: defer the insertion. Spawns are queued in a second vector during the frame and moved into m_entities at exactly one point — after both the entity update loop and the physics pass have finished, when no iterator into the vector is live.

Alternatives considered

OptionWhy it lostWould it win if…
reserve() a large capacity up front Does not fix anything — it makes the reallocation rarer, which is strictly worse than a crash you can reproduce. The 400-entity cap already in the spawn handler means a long fight can still reach any bound you pick. Never. Hiding UB is not fixing it (g-rule-2).
Index-based loop (for (size_t i = 0; i < m_entities.size(); ++i)) Survives reallocation, but only for the loop you remembered to convert. The physics engine iterates the same vector, and so does every future loop anyone adds. It also silently changes semantics: entities spawned this frame would be updated this frame, sometimes. If there were exactly one loop and it would stay that way.
std::list or std::deque for the entity list Both keep references valid across insertion, so this class of bug disappears. But the entity list is walked every frame by physics, collision and rendering; giving up contiguity to fix an ordering mistake trades cache locality for a discipline problem. Make EventBus::publish asynchronous (queue every event) Fixes this and every future variant, but changes the semantics of all 30+ event types at once — sounds, HUD updates and score would all land a frame late, and code that assumes a handler has already run would break invisibly. A larger refactor, worth revisiting if a second ordering bug appears.
Defer only the insertion: a pending-spawn queue chosen — the smallest change that makes the invariant structural rather than remembered. Every spawn already goes through one door (queueSpawn), so there is nowhere for a future spawn to bypass it, and the vector stays contiguous. —

3 · CS & Math Foundations

Why push_back ever moves anything: amortised growth

std::vector guarantees contiguous storage. To keep push_back amortised O(1) despite that, implementations grow the buffer geometrically: on overflow they allocate k·capacity for some k > 1 (libc++ and libstdc++ use k = 2; MSVC uses k = 1.5), move the elements across, and free the old block.

Cost of n push_backs starting from capacity 1, growth factor k: reallocations occur at sizes 1, k, k², …, k^m where k^m ≤ n total elements moved = 1 + k + k² + … + k^m = (k^(m+1) - 1) / (k - 1) < n·k / (k - 1) k = 2 -> < 2n moves k = 1.5 -> < 3n moves Therefore total = O(n), amortised O(1) per push_back — but the WORST CASE of a single push_back is O(n), and that worst case is exactly the one that invalidates every iterator.

The bound is what makes the bug intermittent. Reallocation happens on O(logk n) of the n insertions — roughly 20 times over a million push_backs — so a loop that appends per iteration is safe almost every time and catastrophic occasionally. That is the profile of the reported symptom exactly: fine for a while, then a crash.

What the standard actually says

Reallocation invalidates all references, pointers, and iterators referring to the elements in the sequence. — [vector.modifiers] on insert/push_back

A range-for is defined to be an iterator loop: for (auto& e : v) caches v.begin() and v.end() once, before the body runs. So after a reallocating push_back in the body, both cached iterators point into the freed block. Incrementing one is undefined; dereferencing it reads memory the allocator has taken back.

Why macOS survived and Windows did not

Nothing in the standard makes either behaviour correct — but the observed difference has a mundane cause. Freed memory is not scrubbed. Whether the stale iterator reads plausible data or faults depends on whether the allocator has reused or unmapped that page, which differs between libc++/malloc on macOS and the MSVC STL on Windows; and MSVC's debug iterators (_ITERATOR_DEBUG_LEVEL) actively check for invalidation and abort. So the same UB is silent on one toolchain and a hard crash on the other.

Cost of the fix. The queue adds one move per spawned entity and one reserve-backed append per frame: O(s) time for s spawns, O(s) extra space, with s bounded by the existing 400-entity cap. The per-frame cost when nothing spawns is a single empty() check.

a. The loops that must not be disturbed

The two loops that walk m_entities every frame — SuperMarioGame/src/Core/PlayingState.cpp:630-638 @ 4f80862
    // 3. Update all active entities
    for (auto& entity : m_entities) {
        if (entity && entity->isActive()) {
            entity->update(dt);
        }
    }

    // 3. Run the physics engine pipeline (apply gravity, integrate velocity, check/resolve collisions)
    m_physicsEngine.update(m_entities, m_tileMap, dt);
What it does: updates every active entity, then hands the same vector to the physics engine for integration and collision resolution.
Why it matters: for (auto& entity : m_entities) is defined to cache begin() and end() before the body runs, so for the whole duration of both statements there are live iterators into m_entities's buffer. Note that m_physicsEngine.update takes the vector by reference and walks it too — converting only the visible for to an index loop would have fixed half the bug.

b. Why a handler runs inside that loop

EventBus::publish — delivery is synchronous, on the caller's stack — SuperMarioGame/src/Core/EventBus.cpp:33-60 @ f0a61f4
void EventBus::publish(const GameEvent& event) {
    auto it = m_subscribers.find(event.type);
    if (it == m_subscribers.end()) return;

    ++m_publishDepth;

    // Iterate by index over the live vector rather than over a copy.
    //
    // This used to copy the whole subscriber vector on every publish, which
    // copies a std::function per subscriber — a heap allocation each, on an
    // event bus that fires on every coin, stomp, block and jump (audit X-7). The
    // copy was there to survive a handler unsubscribing mid-delivery; the
    // tombstone in unsubscribe() handles that without copying anything.
    //
    // The size is taken once, so a handler that subscribes during delivery does
    // not receive the event it is currently handling — which would otherwise be
    // an easy accidental infinite loop.
    std::vector<Subscription>& subs = it->second;
    const std::size_t count = subs.size();
    for (std::size_t i = 0; i < count && i < subs.size(); ++i) {
        // Re-checked each step: a handler may append, which can reallocate.
        if (!subs[i].alive || !subs[i].callback) continue;
        subs[i].callback(event);
    }

    --m_publishDepth;
    if (m_publishDepth == 0 && m_needsCompaction) compact();
}
What it does: walks the subscriber vector by index and calls each live callback.
Why this way: synchronous delivery is the point of this bus — a sound cue that arrived a frame after the coin would be wrong. Notice the care already taken for this vector: count is captured once and re-checked against subs.size() each step, precisely because "a handler may append, which can reallocate". The same hazard for m_entities was not noticed, which is what this record is about: the danger was understood locally and missed globally.

c. The fix: one door in, one point of admission

The fix: queueSpawn() and flushPendingSpawns() — SuperMarioGame/src/Core/PlayingState.cpp:2684-2704 @ 4f80862
void PlayingState::queueSpawn(std::unique_ptr<Entity> entity) {
    if (!entity) return;
    // Wired now rather than at flush time: the spawner may set velocity or read
    // the sprite size straight after this call, and a half-built entity would
    // give it the wrong answer.
    admitEntity(entity.get());
    m_pendingSpawns.push_back(std::move(entity));
}

void PlayingState::flushPendingSpawns() {
    if (m_pendingSpawns.empty()) return;
    // Moved out first: admitting an entity cannot itself spawn one today, but if
    // it ever does, that spawn lands in a fresh queue for the next flush rather
    // than growing the vector this loop is walking.
    std::vector<std::unique_ptr<Entity>> ready;
    ready.swap(m_pendingSpawns);
    m_entities.reserve(m_entities.size() + ready.size());
    for (auto& entity : ready) {
        if (entity) m_entities.push_back(std::move(entity));
    }
}
What it does: queueSpawn wires the entity's animations and difficulty immediately — so a caller that reads its sprite size or sets its velocity straight afterwards still gets a fully-formed object — then parks it in m_pendingSpawns instead of m_entities. flushPendingSpawns moves the queue across in one pass.
Why the ready.swap(): the queue is emptied into a local before the loop that drains it. Admitting an entity cannot itself spawn one today, but if it ever does, that spawn lands in a fresh m_pendingSpawns for the next flush rather than growing the vector this loop is walking — the same mistake one level down. This is the line someone will "simplify" into for (auto& e : m_pendingSpawns); that reintroduces the bug in miniature.

d. The one place the entity list may grow

The one point in the frame where m_entities may grow — SuperMarioGame/src/Core/PlayingState.cpp:640-645 @ 4f80862
    // 3a2. Admit everything a handler asked for during the two loops above.
    //
    // This is the only point in the frame where m_entities is allowed to grow:
    // the entity update loop and the physics pass have both finished, so no
    // iterator or reference into the vector is still live.
    flushPendingSpawns();
What it does: drains the queue after the update loop and the physics pass, before the prune step.
Why here: it is the first point in the frame at which no iterator into m_entities is live. Placing it earlier would defeat the fix; placing it after the prune would let a freshly-spawned entity be pruned before it had ever been updated. An entity spawned on frame n therefore first moves on frame n+1 — a deliberate one-frame latency, invisible at 60 Hz, and the price of the invariant.

Walking the main path

  1. PlayingState::update enters excerpt (a) and begins iterating.
  2. Bowser's fire timer expires; breatheFire() publishes EntitySpawnRequested.
  3. Excerpt (b) delivers it on the same stack, to PlayingState's lambda.
  4. The lambda calls queueSpawn — excerpt (c) — so m_entities is untouched and the loop's iterators stay valid.
  5. The loop finishes; the physics pass finishes.
  6. Excerpt (d) flushes. m_entities may now reallocate freely, because nothing holds an iterator into it.

Why 1-3 and not 1-1. Question blocks also spawn through this route, but a level contains a handful of them and each fires once, so the odds of a given hit being the one that reallocates are small. Bowser fires every 1.2–2.2 s for the entire fight — dozens of appends inside the update loop — so the level reaches a reallocation almost immediately. Deleting him removed the only high-frequency mid-loop spawner in the game, which is why that "fixed" it.

8 · Outcome & Evidence

  • The level runs. tests/scripts/playtest_fixes_1_3.txt drives the game into 1-3 and holds it there for ~11 s, well past Bowser's first several fireballs. Before the fix this is where the Windows build died; after it the run completes and quits cleanly. Verified by running the game, not by building it (g-rule-11, directive 10).
  • The regression is in CI. testMidFrameSpawnsDoNotInvalidateTheEntityLoop in tests/verify_regressions.cpp reproduces the shape of the bug against a std::vector: it starts with size()==capacity(), appends once per iteration of a range-for, and asserts that capacity() is unchanged at the end of the loop and changed after the flush. That second assertion is the one that matters — it proves the unsafe version really would have reallocated mid-loop, so the test is not vacuous.
  • Suite: 13/13 ctest targets pass; 497 checks in the regression binary.
Honest limits of this evidence. The verification runs were on macOS, where the original bug was already invisible — so they demonstrate that the fix does not break anything, not that it cures the Windows crash. The argument that it does is the one in §3: the crash was undefined behaviour caused by reallocation during iteration, and after the change no reallocation can occur while an iterator is live. A Windows playtest of 1-3 is still the outstanding confirmation.

9 · Pitfalls, Misconceptions & Debugging

What went wrong while building it

The bug shipped because the hazard was understood — just not everywhere. EventBus::publish carries a comment explaining that "a handler may append, which can reallocate", and guards its own subscriber vector against exactly that. The same author, in the same file, then wrote three handlers that append to m_entities from inside a loop over m_entities. A local fix to a general problem reads as a solved problem.

It survived review for a second reason: it never failed for the person who wrote it. The macOS allocator absorbed it, and "it works on my machine" is exactly the evidence UB is best at manufacturing.

What a learner is likely to believe wrongly

The plausible-but-false idea: "push_back invalidates iterators only when it reallocates, so if I reserve() enough up front, the loop is safe."

Why it is wrong: it makes the program's correctness depend on a capacity guess holding for every future input. The spawn handler already has a 400-entity cap, so any reserve you pick can be exceeded by a long enough fight; and the next person to add a spawner will not know the guess exists. Worse, it converts a crash into a rare crash — the failure mode moves from "reproducible in 1-3" to "once an hour, in the field". g-rule-2: never mask an error. The invariant has to be structural ("nothing appends while anything iterates"), not statistical.

A second one: "this is a threading bug." There are no threads. The loop is interrupted by a call it made itself. Reaching for a mutex here would add cost and fix nothing.

How it fails at runtime, and how you would debug it

The symptom you would actually observe: not "iterator invalidated". You would see a segfault or an EXCEPTION_ACCESS_VIOLATION deep inside Entity::update or a dynamic_cast, on an entity that looks fine in the level file — or, worse, no crash at all and one entity silently skipped or updated twice. On Windows with a debug STL you would instead get an assertion naming vector iterators.

First three things to check, in order:
  1. Run it under AddressSanitizer (-fsanitize=address). This class of bug is what ASan exists for: it reports heap-use-after-free and prints both the allocation and the deallocation stack — and that second stack is the push_back, which hands you the culprit directly. This should have been step one; the fact that the project had no sanitizer build is the real root cause.
  2. Ask what is different about the failing level. "1-3 crashes, and deleting Bowser fixes it" is not a hint about Bowser — it is a hint about frequency. Look for what the suspect entity does often that others do rarely. Here: it is the only entity that spawns another entity several times per second.
  3. Grep for mutation inside iteration. grep -n 'm_entities.push_back' src/ against the loops in PlayingState::update. Any container mutated by a synchronous callback while a loop over it is live is a candidate, whether or not it is the one crashing today.

10 · Revision Aids

Key takeaways

  1. std::vector grows geometrically, so push_back is amortised O(1) but has an O(n) worst case — and that worst case invalidates every iterator, reference and pointer into the container.
  2. A range-for caches begin() and end() once. Appending inside one is undefined behaviour, not a style problem.
  3. A synchronous observer bus puts the subscriber on the publisher's stack. That is usually what you want, and it means a handler can reach back into whatever the publisher's caller was doing.
  4. Undefined behaviour is allowed to work. A bug that reproduces on one platform and not another is evidence for UB, not against it.
  5. Fix ordering bugs by making the safe ordering structural — one queue, one drain point — not by making the unsafe one less likely.

Self-check questions

  1. The for loop in excerpt (a) was not the only place that walked m_entities during a spawn. Where was the other, and why would converting only the visible loop to an index loop have left the program broken?
  2. flushPendingSpawns swaps the queue into a local before draining it, even though nothing today can spawn during a flush. Argue both sides: what does the swap cost, and what class of bug does it prevent?
  3. With growth factor k and n insertions, how many elements are moved in total, and why does that make this bug intermittent rather than deterministic? Give the sum and the bound.
  4. An entity spawned on frame n is not integrated by the physics engine until frame n+1. Name one gameplay consequence, and explain why it was judged acceptable.

Extension exercises

  1. Add a sanitizer build to CI. Where would you put it, and why must it be a separate job from the normal build rather than a flag on it? (Sketch: a second CMake preset with -fsanitize=address,undefined, a second CI matrix entry; separate because ASan roughly doubles runtime and halves throughput, and because a broken sanitizer build must not block the ordinary one — g-rule-13's hermeticity argument applied to tooling.)
  2. Make the invariant impossible to break rather than merely easy to keep. Today a future author can still write m_entities.push_back directly. How would you prevent it? (Sketch: wrap the vector in a small EntityList type whose push_back is private and whose only friend is flushPendingSpawns; or add a debug-only "iteration depth" counter that asserts on mutation while non-zero. The second catches the physics engine too.)
  3. Remove the one-frame latency. If a spawned projectile had to move on its spawn frame, what would you change, and what new hazard would you have to handle? (Sketch: flush between the update loop and the physics pass instead of after both — safe, since no iterator is live at that point either — but now the physics engine sees entities whose update() has not run this frame, so their strategy state is one step behind their integration.)

Where this sits in the course

CS202 (OOP in C++): the STL sequence containers and their invalidation guarantees; the Observer pattern and the coupling that synchronous notification creates; and object lifetime — this is a use-after-free reached through an iterator rather than through a raw pointer, which is why RAII and unique_ptr did not prevent it. It is also the project's clearest worked example of why directive 10 ("run the game") and a CI gate exist at all.
