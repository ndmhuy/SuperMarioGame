Finding · 20 Aug

The agent fails levels that are provably fine

The first thing the eval runner produced was a contradiction, and resolving it is what separates this project from the papers it started as a reimplementation of.

The heuristic agent finishes none of the four shipped campaign levels. It stalls at 10.8%, 13.8%, 21.4% and 46.4% — in every archetype, having never died. It simply stops making progress and stays stopped for the remaining ~145 seconds.

The geometric oracle says all seven levels are 100% reachable. So the levels are fine and the player is not — but a fitness function built on playthroughs, which is what every system in the bibliography uses, cannot tell those two apart. Used naively, this agent rejects hand-vetted shipped levels as broken, and in a curriculum loop it reports every level as too hard forever.

The oracle put level_1's hardest forced move at column 26. The agent stalls at column 24.25 — at the foot of it. The prediction was independent: the oracle never runs an agent.

Follow-up · traced frame by frame

The agent is not the thing that is broken

A --trace flag on the eval runner turned the stall from a guess into a measurement. The policy is doing exactly the right thing: it reports climbing on every single frame of the stall, and the jump velocity is visibly applied — vy = -678.8, on alternate frames, forever.

The position never changes, and onGround reads false the entire time — while the tile directly below is solid and the 24×30 box is sitting flush on top of it. So canJump is only ever true through flickering coyote frames, and every jump is cancelled by something underneath the policy.

Ruled out along the way: exact-tangency false collisions (AABB::intersects uses strict comparisons), the 0.01px pushback at x=775.99 (ordinary wall resolution), and a ceiling above the agent (the cell is empty, and there is no entity there either). What cancels the applied upward velocity is still open, with the false onGround as prime suspect.

Deliberately not fixed here. The fix lives in PhysicsEngine / CollisionResolver — main-path code — and this branch is contained as a side project. Which branch carries it is a call to make before editing, not after.

Consequence

Measure the level, not the player

solvability.py floods a level with every jump the engine's own physics constants permit — no policy, no learned search, no agent — and answers reachability exactly in about a quarter of a second, against five seconds for one rollout. That splits a single ambiguous signal into three unambiguous ones:

  • Not reachable — broken. Reject it; no agent needed to know.
  • Reachable, agent clears it — too easy for this agent.
  • Reachable, agent fails — the useful case. Real difficulty, and the only rows worth training on.

PAIRED cancels this confound with regret, at the cost of a second trained agent; Volz et al. sidestep it with A*, which is its own kind of competence and costs a search per candidate. Neither removes it.

Difficulty

A bottleneck, not an average

Difficulty is the hardest single move on the kindest route to the goal — a minimax over the reachability graph. Averaging along a path hides the one brutal jump that makes players quit; taking the hardest move anywhere calls a level hard when an easy detour exists.

Two things fall out that no playtest had produced. level_2 and level_3 require a jump at 96% of the physical maximum just to finish — there is no margin; that is not difficulty, it is a level you clear by pixel luck. And there is no difficulty curve, there is a cliff: 0.14 in the sub-levels, 0.71–0.96 in the campaign, nothing in between. Both are direct consequences of a generator that rolls step heights independently of what a player can clear.

Two amendments from what the oracle showed. Sample episodes from campaign levels and the generated pool, as domain randomisation. Curriculum loop

Where the two tracks finally join. Search the generator's latent space for levels the current agent clears 50–70% of the time, train on those, repeat. The band tracks the agent, so yesterday's hard levels fall out of the curriculum automatically as it improves.

Stretch

Containment

How this stays a side project

The risk with two research-flavoured tracks on a coursework game is that they quietly become load-bearing. The branch is stacked rather than merged so the whole experiment stays one droppable unit. 

main ── dev ──┬─ campaign levels, heuristic AI — ships regardless
              └─ A/rl-neural-policy ── A/mapgen-gan   ← side project, both halves
  • No behaviour change on the default path — nothing here runs unless a CLI flag or an explicitly chosen menu entry asks for it.
  • The C++ footprint stays at one flag plus one optional game mode. Training, generation and orchestration are Python, outside the game.
  • Generated levels are additive files, never replacements. level_1 through level_3 stay exactly as they are on dev.
  • The course deliverable never depends on a model training successfully.

The premise

Why the current generator plays badly

MapGenerator.cpp is a single left-to-right pass of independent probability rolls: a sine-wave elevation profile, a per-column pit dice roll, uniform enemy and decoration rates. You can read the consequence straight off the strip at the top of this page — long flat runs, isolated single enemies, and no composed obstacle anywhere.

Structurally it cannot express rhythm (the setup–challenge–reward phrasing real levels alternate), an intra-level difficulty curve (column 20 and column 180 are drawn from the same distribution), or a composed challenge (a gap and an enemy and a moving platform arranged as one obstacle). A learned generator attacks all three, because it learns tile co-occurrence structure from real levels.

What it does not fix is solvability — a generator knows what levels look like, never what they play like. That is permanently the agent's job, which is why the agent-filter stage stays in the pipeline whichever generator wins.
