## Issues & Resolutions

### **Issue 1: QuestionBlock and Static Blocks Accelerating into Void**
* **Problem**: `QuestionBlock`, `BrickBlock`, and other block entities inherited from `Block` (which derives from `Entity`). Because `Block` did not override `getGravityMultiplier()`, it defaulted to `1.0f`. During runtime physics updates, `PhysicsEngine::applyGravity()` applied downward acceleration ($g = 1800 \text{ px/s}^2$) to static blocks, causing question blocks to detach from the level layout and accelerate into the void.
* **Resolution**: Overrode `getGravityMultiplier() const override { return 0.0f; }` in [Block.hpp](../../SuperMarioGame/include/Entities/Block.hpp). Updated `PhysicsEngine::update()` to check `if (entity->getGravityMultiplier() > 0.0f)` before accumulating downward gravitational velocity, ensuring static blocks remain permanently anchored.

### **Issue 2: Spawned Items Slipping Through Solid Block Platforms**
* **Problem**: Power-up `Mushroom` and `FireFlower` items dispensed from question blocks lacked a dedicated resting state flag. `CollisionResolver::resolveEntityVsTile()` only corrected terrain tile penetrations without zeroing accumulated downward velocity, allowing moving items to slip through block seams and plunge into the abyss.
* **Resolution**: Added `m_onGround` boolean flag to [Item.hpp](../../SuperMarioGame/include/Entities/Item.hpp). Implemented `CollisionResolver::resolveItemVsBlock()` to handle item-to-block collision responses, setting vertical velocity $v_y = 0$ and `m_onGround = true`. Updated `PhysicsEngine::applyGravity()` to bypass gravity accumulation when an item is confirmed resting on a solid surface.

### **Issue 3: Player Hitbox Width Preventing 1-Block Chute Descent & Gap Traversal**
* **Problem**: The player collision bounding box was initialized to $32 \times 32$ px (and $32 \times 64$ px for Super/Fire forms). Because grid tiles and vertical shaft openings are exactly 32 px wide ($1 \text{ tile} = 32 \text{ px}$), entering a 1-tile drop-down chute or jumping across 1-tile gaps caused micro-pixel corner snags against adjacent block AABBs, preventing Mario from entering pipes or falling through 1-block shafts.
* **Resolution**: Optimized player collision box dimensions in [IPlayerState.cpp](../../SuperMarioGame/src/Entities/IPlayerState.cpp) to $24 \times 30$ px for Small Mario, $24 \times 60$ px for Super/Fire/Cape Mario, and $14 \times 14$ px for Mini Mario, centered horizontally within the 32px sprite width with 4px margins on each side. This provides clean clearance for vertical descent and gap jumps without tile edge snagging.

### **Issue 4: LevelLoader `std::ifstream` Failbit Cascade on Multi-Path Probing**
* **Problem**: In `LevelLoader::loadLevel()`, candidate paths were checked sequentially in a loop using `file.open(candidate)`. When the first candidate path failed to open, `std::ifstream` set its internal `failbit`. Subsequent calls to `file.open()` with valid fallback paths were silently ignored because the stream error state was not cleared, causing runtime failures when opening sub-level maps (e.g. `assets/levels/level_1_sub.json`).
* **Resolution**: Added `file.clear()` before each `file.open()` iteration in [LevelLoader.cpp](../../SuperMarioGame/src/Utils/LevelLoader.cpp). Expanded fallback candidate search paths to include `build/assets/levels/`, `../build/assets/levels/`, `../assets/levels/`, and `assets/levels/`, ensuring level loading succeeds regardless of whether the executable is launched from the workspace root or the build directory.

### **Issue 5: Application Exit Crash from Static SFContext Destruction (`SIGABRT`)**
* **Problem**: Closing the game window caused static destruction order collisions where SFML's internal OpenGL context (`SFContext`) was terminated while the active `sf::RenderWindow` still held OpenGL handles, producing an immediate `SIGABRT` crash during program exit.
* **Resolution**: Updated `Game::shutdown()` in [Game.cpp](../../SuperMarioGame/src/Core/Game.cpp) to explicitly invoke `m_window.close()` before popping state stacks and shutting down manager singletons, ensuring all OpenGL context references are cleanly relinquished prior to static teardown.
