## Issues & Resolutions

### **Issue 1: Level-Completion Gate Absent, Stale Camera Mode, and Player Z-Order Inversion**
* **Problem**: Three defects shared one investigation. (a) `level_2.json`/`level_3.json` placed their castle with only 0.5 tiles of buffer to the level's right edge (`level_1.json`/`bonus_1.json` have 8.5), and the level-complete sequence gave the player no walk-to-the-door beat on any stage, so the end-of-level walk drove the player into the castle wall. (b) Boom Boom's arena (`arenaX 185, arenaW 11`) spanned past the flagpole at `x=193`, so the "no escape until defeated" clamp still let a player reach a touchable flag with the boss alive. (c) `PlayingState::setupTestScene()` never reset the camera's `ScrollMode` or position on a new level load, so a `Locked` mode left over from a boss arena carried into the next level, and `adoptPlayer()` inserting the player at the front of `m_entities` meant `render()`'s draw-in-list-order painted later entities (bosses) over the player, making them invisible.
* **Resolution**: Widened `level_2.json`/`level_3.json` from 200 to 208 tiles (only the spans already touching the old edge) to restore the castle buffer; shrank Boom Boom's `arenaW` from 11 to 7, leaving a 1-tile gap before the flagpole (mirroring `level_3.json`'s own Bowser arena); added a code-level gate in `PlayingState`'s `LevelComplete` subscriber that refuses completion while `m_activeBoss` is active, independent of level data; gave the level-complete hold a real "walk to the castle door" sequence driven by `moveLeft()`/`moveRight()`; made `setupTestScene()` unconditionally reset the camera to `Free` mode and snap it to the new level's spawn point on both the success and fallback paths; reordered `render()` to draw `m_player`/`m_player2` after the general entity loop. Verified live via `tests/scripts/verify_1_3_camera_and_visibility.txt` (confirmed 1-3 opens on the player's own spawn corner and the player stays visible over foreground entities) plus 13 new/strengthened ctest cases; the scripted run did not survive far enough to reach Bowser himself, so that specific frame rests on the ctest case and code review only — noted honestly in [`docs/verification/README.md`](../../docs/verification/README.md) rather than claimed as observed.

### **Issue 2: One Bug Reported as Three — the Dual-Write Asset Tree**
* **Problem**: [`tools/generate_game_levels.cpp`](../../SuperMarioGame/tools/generate_game_levels.cpp) wrote every level twice — once relative to the working directory and once to `"../" + path` — creating an untracked second `assets/levels/` tree at the repository root. `ResourceManager::resolvePath` tries the bare relative path **first**, so which tree the game read depended entirely on the launch directory: from `SuperMarioGame/` the tracked tree (correct); from the repo root, the stray tree (stale). The stray tree was frozen at 2026-08-31 12:35, **nine minutes before** the two commits (`309c1a5`, `cc6a32d`) that fixed the exact defects it still contained (P-Switch deleting sub-level floors; a 1-column "half" entrance pipe), and had flattened every level's `theme` to `overworld`. Three separately-reported bugs — half pipes, a broken 1-1 Sub P-Switch, and "two sources of truth for asset detail" — were one bug: whoever filed a report and whoever tried to reproduce it were not necessarily running the same files.
* **Resolution**: Deleted the dual write from `generate_game_levels.cpp`; gitignored `/assets/` at the repository root (anchored, not recursive, so the tracked `SuperMarioGame/assets/` is untouched); added [`tests/guard_asset_single_source.cpp`](../../SuperMarioGame/tests/guard_asset_single_source.cpp), which fails the build if a second tree reappears and also asserts the canonical tree is intact (so deleting the *right* tree cannot silently pass). The stray tree was backed up outside the repository before removal and the deletion was explicitly approved by the user, per AGENTS.md directive 7 (never discard uncommitted work without confirmation).

### **Issue 3: Game `SIGABRT`s on Startup With No Audio Playback Device**
* **Problem**: `SoundManager::getInstance()` built a pool of 64 real `sf::Sound` objects at construction time regardless of hardware. On a machine (or CI runner) with no sound card, SFML's `miniaudio` backend fails to open a playback device and drives the process to `SIGABRT` before the first test assertion runs — the reason `.github/workflows/ci.yml` had been installing a dummy ALSA device as a workaround instead of the game handling the absence itself.
* **Resolution**: Added `SoundManager::m_audioAvailable`, probed exactly once in the constructor via `sf::PlaybackDevice::getDefaultDevice().has_value()` (confirmed safe against SFML 3.0.2's vendored source — this call only enumerates and logs, never throws). When unavailable, the `sf::Sound` pool is skipped entirely and `playSound()`/`playMusic()` become no-ops; `stopMusic()`/`pauseMusic()`/`resumeMusic()` were deliberately left unguarded since SFML already no-ops those on a never-opened `sf::Music`. Verified with two manual runs — unmodified (reaches `MenuState` silently) and with the probe hardcoded false (reaches `MenuState` with exactly one "running silent" warning, no abort) — since macOS provides no way to actually remove the audio device for a true device-less test.

### **Issue 4: `SIGSEGV` at Program Exit After Migrating to `ScopedSubscription`**
* **Problem**: Converting `AchievementManager`/`StatisticsTracker`'s subscriptions from raw `EventBus::SubscriptionId` to `std::vector<EventBus::ScopedSubscription>` turned `verify_save_load`'s `testTrackerAndAchievements` into a reliable `SIGSEGV` (ctest exit 139) at program exit. `EventBus::ScopedSubscription`'s destructor calls `EventBus::getInstance().unsubscribe()`, and a vector of them owned by a Meyers-singleton destructs at static-destruction time; function-local statics destruct in reverse order of first construction, and which of `EventBus`'s-or-a-singleton's static constructs first depends on runtime call order, not anything a caller controls. `EventBus`'s static could already be destroyed by the time a singleton's `ScopedSubscription`s destructed, and calling `EventBus::getInstance()` again on a dead function-local static is undefined behaviour.
* **Resolution**: Added a `bool g_eventBusAlive = true` (constant-initialized, safe to read from any other destructor regardless of order), flipped `false` in a newly-added `~EventBus()`, and checked by `ScopedSubscription::reset()` before it touches `EventBus::getInstance()`. Re-verified: `./verify_save_load` exits 0 across three repeated runs, ctest back to 13/13.

### **Issue 5: 28 `dynamic_cast`s in `CollisionResolver.cpp`**
* **Problem**: Type dispatch by `dynamic_cast` chain outside the resolver's own ordered `EntityCategory`-pair switch had crept back to 28 hits in `CollisionResolver.cpp`, against a plan target of fewer than 4 — a live erosion of the R5 collision-dispatch refactor's Open/Closed intent (SPEC's own audit had separately flagged this as D8/A-10).
* **Resolution**: Replaced the cast chains with virtual contact hooks on `Entity` (`onStomped`, `onHitFromBelow`, `onPlayerTouch`, etc.) dispatched through the existing ordered `EntityCategory`-pair switch, per member_a_fix_plan.md WP12's acceptance bar. One dispatch family fixed per commit, with a full rebuild and full ctest run after each, per the orchestrating session's explicit discipline; a cast was kept, and documented as the honest answer, wherever it was genuinely the simplest correct option rather than forced to zero for the sake of the count.

### **Issue 6: The ctest Suite Passed Vacuously Under a Release Build**
* **Problem**: `CMAKE_BUILD_TYPE=Release`'s stock `-O3 -DNDEBUG` compiles every `assert()` in the `verify_*` harnesses (`verify_all` 54 assertions, `verify_enemies` 48, `verify_save_load` 32, `verify_blocks` 20, etc.) to nothing, so those targets printed `PASSED` and exited 0 without evaluating a single assertion — proven empirically during R5 by mutating `HiddenBlock` and watching the suite stay green.
* **Resolution**: Stripped `NDEBUG` from test targets only, at the `add_verify_test()` chokepoint in [`SuperMarioGame/CMakeLists.txt`](../../SuperMarioGame/CMakeLists.txt) (`target_compile_options(${name} PRIVATE -UNDEBUG)`), deliberately choosing this over rewriting ~230 `assert()` call sites to a `check()` helper — the game binary itself keeps `NDEBUG` (assertions in shipped code stay compiled out, as intended). Verified by mutation: baseline the bug, fix it, re-break it, revert, confirming the guard actually fails when it should.

### **Issue 7: A Boss Pushed Out of Its Arena Falls Forever**
* **Problem**: A user-reported live session (with screenshot) showed the Bowser health bar still on-screen while Bowser himself had fallen out of the level entirely, with no way to end the encounter — the boss had been physically knocked or walked past its arena's bounds with nothing to stop it falling indefinitely off-screen.
* **Resolution**: Added `Boss::returnToArenaSpawn()` in [`Entities/Boss.cpp`](../../SuperMarioGame/src/Entities/Boss.cpp), teleporting a boss that leaves its arena's bounds back to its spawn point instead of leaving it to fall forever. This same method became the template for the R21 batch's `DebugCheats` immortality rescue (Task 27 above), which explicitly cites it as the existing solution to "falls out of the playable area" that the player itself had never been given.

### **Issue 8: Map Editor Palette Silently Placed Nothing for 24 of 40 Buttons**
* **Problem**: `PlaceEntityCommand` hand-rolled 16 type names in a `switch` and never called `EntityFactory::create` — the one path every other spawner in the codebase uses. The test that looked like it covered this actually called `EntityFactory::create` directly (the path placement did **not** use), while its own comment described this exact failure mode. Net effect: 24 of the editor's 40 palette buttons placed nothing, silently.
* **Resolution**: Rebuilt the editor as a real [`Core::EditorState : IGameState`](../../SuperMarioGame/include/Core/EditorState.hpp) that places entities through `EntityFactory::create` (backed by the new `EntityCatalogue` registry from Task 25), closing the type-list drift permanently since the registry is now the single source both the factory and the editor read. Also closed a use-after-free found during this work: `forgetEntity` handled the boss/shadow/player-2 raw pointers but not Player 1, so erasing Mario left three dangling raw pointers into `m_entities`.

### **Issue 9: Bowser's Fireball Stagger Was the Inverse of the Reported Bug**
* **Problem**: Reported as "Bowser does not receive fireballs but can still be stomped." The enclosure-post hypothesis was tested and refuted both geometrically and empirically (a fireball registers hit on frame 0). The real defect was the **inverse** of the report: a bursting fireball stayed collidable through its full 0.24s explosion animation, so a single shot scored three hits against Bowser's stagger counter — invisible on an ordinary enemy, which dies to the very first hit. Because Bowser closes to melee range in roughly one second and every player-boss contact costs a form, and `onTookHit()` also zeroed the player's own fire-flower count on a successful stomp, the fight was winnable only by an undesigned route (repeated stomping) and effectively unwinnable by its designed one (four fireballs to stagger, then stomp).
* **Resolution**: Gated Bowser's stomp-vulnerability behind a stagger state exposed as a virtual on `Boss` rather than a `dynamic_cast` in the resolver, and fixed the fireball hit-window so a single burst can only register once. Paired with Lakitu now dropping a Fire Flower (Task 29) so the fight has a guaranteed, repeatable route to the fireballs the stagger requires even after a player has lost their power-up 114 tiles back. Verified live: fireballs 1→2→3→4 staggering Bowser with the HUD counting down to "STUNNED - STOMP NOW", and contact refused while he is guarded.

### **Issue 10: Two-Player Camera Froze After an Elimination**
* **Problem**: The camera dispatch chose `updateVersusCamera` on `m_player2` alone whenever both players existed; when P2 was eliminated, that call returned early because it required both players, and the lone-player tether path had a mirrored version of the same bug — so the surviving player got neither camera. `updateBossArena`/`releaseBossArena` also read `m_player` directly rather than the active participant, so arena lock, escape clamp and battle music went dead for a 2P boss-fight survivor. Separately, P1's HUD badge went stale showing `setupTestScene`'s mock values in a real run, and P2's badge vanished entirely on elimination rather than showing an eliminated state.
* **Resolution**: Added `PlayingState::activeParticipant()` so camera, arena and music logic all resolve the live player rather than assuming both exist; added `rememberEliminatedIdentity()`/`applyEliminatedBadges()` to retain an eliminated player's HUD identity before `destroy()` nulls the pointer, so the badge can dim and stamp "OUT" instead of disappearing. Verified live: MARIO's badge dimmed with a red "OUT" while P2 continued playing and the terrain scrolled correctly behind the survivor.

### **Issue 11: A Flagpole Touched During a Boss Fight Permanently Disabled Itself**
* **Problem**: `Flagpole::onPlayerCollision` latched `m_triggered`, paid the score, and published `LevelComplete` unconditionally on first touch. `PlayingState`'s handler then refuses that completion while a boss is alive (SPEC 6.4, "no escape until defeated") — but the latch stayed set regardless, so every later touch hit `if (m_triggered) return;` and published nothing. A player who brushed the flag mid-fight (level_2's Boom Boom arena spans tiles 176–192; the flagpole stands at 193, one tile past the fight's movement clamp) permanently spent the flagpole: boss dead, flag present, level impossible to finish. The refused touch also paid 5000 points and played the flagpole jingle, so it looked like something had succeeded, which is why one player reproduced the bug and the reporting teammate could not.
* **Resolution**: Both the collision handler and the gate now call one shared `levelMayComplete()` rather than maintaining two independent copies of "may the level end now" (a class of duplication this batch had already paid for more than once). A refused touch now leaves no trace at all — no latch set, no score paid, no jingle played — and `PlayingState` installs the completion gate on every `Flagpole` through `admitEntity`, the same single door the difficulty scale uses, so an editor-placed flagpole and a level-loaded one are gated identically. ctest 28/28 → 29/29 (new case in [`tests/verify_r21_flagpole_softlock.cpp`](../../SuperMarioGame/tests/verify_r21_flagpole_softlock.cpp)).
